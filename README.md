# Recur

A chat app that notices when you keep asking for the same *kind* of thing, and
offers to compile it into a small reusable tool instead of solving it from
scratch every time. This is a real two-process app: an Express + JSON-file
backend, and a React (Vite) frontend. No Claude-specific runtime, no artifact
sandbox. It is yours to run, host, and modify.

Tested end-to-end in this environment: registration, login (JWT in an
httpOnly cookie), chat creation/persistence, and error handling all verified
working. The one thing *not* verified here is a live model reply, because
this sandbox can't reach the OpenAI/Anthropic API. On your own machine it
will just work once a key is connected on the Integrations page or set in
`server/.env`.

## How it's organized

```
recur/
  server/     Express API + JSON-file database (lowdb) + your LLM calls
  client/     React (Vite) frontend
```

There's no shared build step. They are two independent Node projects that
talk over HTTP. Run both at once during development.

## 1. Backend

```bash
cd server
npm install
cp .env.example .env
```

Open `server/.env` and set:

```
PROVIDER=openai            # or "anthropic"
API_KEY=sk-...             # optional, a server-wide fallback key
```

The `API_KEY` in `.env` is now optional. If you leave it out, every person
using the app connects their own key on the Integrations page instead, and
the server starts with a warning instead of failing. Everything else in
`.env` has a sane default. Then:

```bash
npm run dev
```

This starts the API at `http://localhost:8787`, and creates
`server/data/db.json` on first write, a plain JSON file holding users (each
with their optional saved key), chats, the compiled tool library, and the
execution log. No external database to install. (Fine for personal use / a
small group; if you want this in front of real traffic, swap `db.js` for a
real database. Every other file only talks to `db.data`, so that's the one
file to change.)

## 2. Frontend

In a second terminal:

```bash
cd client
npm install
npm run dev
```

Open `http://localhost:5173`. In dev, Vite proxies `/api/*` to the backend
on port 8787 (see `client/vite.config.js`), so both need to be running.

## 3. Use it

Register an account, connect a key on the **Integrations** page (OpenAI or
Anthropic, with a Test button to check it before saving), then just chat.
A few things to try:

- Send three differently worded versions of the same kind of task (e.g.
  "Is this urgent?", "Does this need immediate attention?", "Should this be
  escalated?"). On the third one, Recur will offer to compile a tool from
  the pattern. You can accept, decline, or ask it to clarify first.
- Once a tool exists, send another task like the ones it was built from.
  Recur will offer to reuse it instead of reasoning from scratch, and you
  choose.
- The **Tool Registry** page shows the shared registry: every compiled
  tool, how many times it's run, and average latency for compiled-tool
  replies vs. general reasoning, a real measured comparison rather than a
  simulated one.
- The model picker (top left) chooses which speed tier general reasoning
  runs on (`quick` / `default` / `complex`, each mapped to a real model in
  `server/.env`). Compiled tools always run on the `quick` tier, which is
  the whole point of compiling one.

## What "compiled tool" actually means here

Not literal model weights. There's no training step. A compiled tool is a
generalized specification plus a couple of examples, generated by asking the
model to describe the pattern across a few similar requests, then run on the
fastest tier as a narrow, specialized prompt instead of a general one. The
speed and latency numbers you see are real and measured, not scripted, but
it's an honest simplification of "compiling a neural program," not the real
thing. Worth saying explicitly if you show this to anyone.

The matching layer is a small, dependency-free embedding system in
`server/src/embeddings.js`: hashed bag-of-words plus character bigrams over
192 dimensions, compared with cosine similarity, with thresholds of 0.6 for
tool reuse, 0.55 for pattern clustering, and a cluster size of 3 before
compilation is offered. All three are constants at the top of
`server/src/engine.js`.

## Data & privacy

- Chats are private per account (`userId` scoped, enforced server-side on
  every route).
- The tool registry (`tools`, `pending`, `log`) is shared across every
  account on this server, by design. The point is a library everyone
  contributes to and benefits from.
- API keys saved on the Integrations page are stored in the server's local
  database, tied to the account that saved them, and are only ever sent
  back to the client masked to their last four characters. For anything
  beyond a trusted local deployment, encrypt them at rest or move them into
  a secrets manager.
- Passwords are hashed with bcrypt; sessions are a JWT in an httpOnly
  cookie, not `localStorage`.

## Deploying it for real

- Set `NODE_ENV=production` and a long random `JWT_SECRET` in `server/.env`.
- Put the backend behind HTTPS (the auth cookie is marked `secure` in
  production, so it won't be sent over plain HTTP).
- `cd client && npm run build` produces static files in `client/dist/`.
  Serve them from any static host or from Express itself (add
  `express.static('../client/dist')` and a catch-all route in
  `server/src/index.js` if you want one process instead of two).
- Swap `server/src/db.js` for a real database if you expect concurrent
  writes at any scale. The JSON file is fine for one machine and modest
  traffic, not for a cluster.
